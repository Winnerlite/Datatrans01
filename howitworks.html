1. The Two Price Tiers

The calculator on my site uses two sources of pricing:

Direct Fare

The real, verified price. Comes from the routePrices object in ngr.json.

Example: routePrices["Lagos-Onitsha"]["ABC Transport"] = 29120

Est. Base Fare

A fallback estimate. Uses the company's basePrice field, which is the same for every route.

Example: transportCompanies["ABC Transport"].basePrice = 23904

Which one is used

  1. 1. If routePrices[from-to] exists → show Direct for companies listed there
  2. 2. Any company NOT listed gets Est. using its base price
Important: the API always returns direct prices only. The Est. tier is a client-side calculation — only my own calculateTrip() uses it. API clients never see "Est. Base Fare" in responses.

2. How to Add a New Direct Route

Edit ngr.json, find the routePrices object, add a new entry:

"routePrices": {
  "Lagos-Onitsha": {
    "ABC Transport": 29120,
    "God is Good Motors": 36400,
    "Chisco Transport": 25480,
    "GUO Transport": 35490,
    "Peace Mass Transit": 22750
  }
}
After saving: reload the site, search Lagos → Onitsha. Those companies now show "Direct Fare".
Watch out: the route key must match exactly. Lagos-Onitsha ✅ · Lagos - Onitsha ❌ · lagos-onitsha ❌
Naming rule: FromState-ToState with a hyphen, no spaces. Direction matters — Lagos-Onitsha and Onitsha-Lagos are separate entries.

3. The Company Name Matching Problem

The same company can appear with different names in routePrices vs transportCompanies. This causes silent duplicates or mismatches.

Real example:

In routePrices:

"Young Shall Grow"

In transportCompanies:

"The Young Shall Grow Motors"

Fix: the ALIASES object in calculateTrip() maps variants to the canonical name:

const ALIASES = {
  "Young Shall Grow": "The Young Shall Grow Motors",
  "The Young Shall Grow": "The Young Shall Grow Motors",
  "The Young Shall Grow Motors": "The Young Shall Grow Motors",
  "GIGM": "God is Good Motors",
  "Nsik": "Nsik Motors (AKTC)"
};

4. Access Control — Three Paths

Every request to the API comes through one of three doors. Each door has a different rule.

🏠

Path 1 — My Own Website

Requests from intercityprices.com.ng or www.intercityprices.com.ng.

Check

Origin in ALLOWED_ORIGINS

Requires key?

No

📦

Path 2 — Zyla / RapidAPI

Requests forwarded from vyrametrics.vercel.app by Zyla or RapidAPI's servers.

Check

x-proxy-secret matches PROXY_SECRET env var

Requires key?

No (secret instead)

🔑

Path 3 — Direct Clients

Anyone else — clients I onboarded, or attackers trying their luck.

Check

x-api-key is in CLIENT_KEYS

Requires key?

Yes

Order matters: The verify function checks Zyla first, then the client key, then the origin whitelist. This means a client with a valid key can call from any domain (including my own), and Zyla always works even without a client key.
Known limitation: Someone can fake the Origin header with curl to look like my own website. But that same person could also just fake the x-api-key header if they knew a client's key. Neither is possible without knowing a secret. Not worth defending against right now.

File structure

├── companies.js           ← uses verifyAccess()
└── routes.js              ← uses verifyAccess()

ngr.json                   ← all data (companies, states, routes, prices)

🔑 Client Keys

Stored in api/_lib/clients.js:

const CLIENT_KEYS = {
  'vyra_live_acme_8f3k2n9p4q':      'Acme Travels',
  'vyra_live_naija_2h7m5v1x8c':     'Naija Booking',
};

Key format: vyra_live_<shortname>_<random>. The value (right side) is only used for logging.

🌐 Website Whitelist

Also in api/_lib/clients.js:

const ALLOWED_ORIGINS = [
  'https://www.intercityprices.com.ng',
  'https://intercityprices.com.ng',
  'http://localhost:3000',
  'http://localhost:5500',
];

Only matters for browser calls from my own site. Clients with keys don't need to be listed here.

🔒 Zyla/RapidAPI Secret

Stored in Vercel Environment Variables:

Vercel Dashboard → Project → Settings → Environment Variables

PROXY_SECRET = "..."

Never write this in code. Never share it. Zyla/RapidAPI already have it configured on their side.

6. Onboarding a New API Client

Repeat per client

When someone pays to integrate the API, follow these steps.

Step 1 — Generate a key

Format: vyra_live_<shortname>_<random>

Any random string works. Examples:

vyra_live_acme_8f3k2n9p4q
vyra_live_naijabook_2h7m5v1x8c
vyra_live_giglog_b4t9w6y3r7

Step 2 — Add it to _lib/clients.js

Open api/_lib/clients.js, add one line to CLIENT_KEYS:

const CLIENT_KEYS = {
  'vyra_live_acme_8f3k2n9p4q':      'Acme Travels',
  'vyra_live_naijabook_2h7m5v1x8c': 'Naija Booking',   // ← new client
};

The right-side value is just for logging — use the client's business name.

Step 3 — Push to git

Commit and push. Vercel auto-deploys in ~30 seconds. The key is live.

Step 4 — Send them the email

Use the template in Section 8.

Step 5 — Confirm they can call the API

Test from your own terminal first:

curl -H "x-api-key: vyra_live_acme_8f3k2n9p4q" \
     "https://www.intercityprices.com.ng/api/states"

If you get JSON back, the key is working. Now let the client test.

Step 6 — Log it below

Add a row to the client log.

Keep this updated. Remove rows when a client leaves.

Client Key Date Added Status
No clients yet — add a row when you onboard one.

7. Removing a Client

When a client stops paying or asks to be removed:

Step 1 — Delete their line from CLIENT_KEYS

Open api/_lib/clients.js, remove their entry. Optionally leave it as a comment with the removal date:

const CLIENT_KEYS = {
  'vyra_live_naijabook_2h7m5v1x8c': 'Naija Booking',
  // 'vyra_live_acme_8f3k2n9p4q':   'Acme Travels (removed 2026-06-15)',
};

Step 2 — Push to git

Their key stops working within 30 seconds. Any subsequent request returns 403 Invalid or revoked API key.

Step 3 — Mark them removed in the client log

Update the table above with a "Removed" status and date.

That's it. No database, no dashboard, no dashboard. One file edit + push.

Example request:

curl -H "x-api-key: vyra_live_theirname_xxxxxxxxxx" \
"https://www.intercityprices.com.ng/api/search?q=Lagos"

Available endpoints:

  • GET /api/search?q={query} — search states, companies, routes
  • GET /api/transport — full dataset (cache this)
  • GET /api/states — all states
  • GET /api/states?state=Lagos — one state
  • GET /api/companies — all companies
  • GET /api/routes?from=Lagos&to=Abuja — route prices

Documentation: www.intercityprices.com.ng/apifordevs.html

Live tester: www.intercityprices.com.ng/api-test.html

Tip: if your frontend calls the API directly, we recommend proxying through your backend so the key stays server-side. If your users can see the key in DevTools, they can copy it.
